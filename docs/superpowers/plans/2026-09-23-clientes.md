# Clientes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Asociar ventas a un cliente identificado por teléfono (alta rápida sin salir del carrito) y agregar una pantalla `/clientes` con estadísticas por cliente (compras, gasto total, recurrencia).

**Architecture:** Sigue el mismo patrón que el resto del proyecto — Server Components para lecturas (`server/queries/customers.ts`), Server Actions para escrituras (`server/actions/customers.ts`, y una extensión de `createSale` ya existente), y una tabla `Customer` que se **adopta** de una que ya existe en producción (huérfana, sin filas) en vez de crearse desde cero.

**Tech Stack:** Igual que el resto — Next.js 16 App Router, Prisma + PostgreSQL, Zod, Tailwind v4, Vitest + RTL.

**Spec:** `docs/superpowers/specs/2026-09-23-clientes-design.md` — leer antes de ejecutar.

## Global Constraints

- **Next.js 16 — APIs cambiadas.** Server Actions son invocables directo desde componentes cliente.
- **Toda Server Action mutante empieza con `await requireRole([...])`** — sin excepción.
- **Toda escritura de `Customer` durante una venta ocurre dentro de la misma `prisma.$transaction` que crea la `Sale`** — nunca un cliente nuevo sin la venta que lo originó, ni viceversa.
- **El teléfono se normaliza (solo dígitos) antes de cualquier lectura o escritura de `Customer.phone`** — nunca comparar/guardar el string crudo.
- **La migración de esta iteración es idempotente para la tabla `Customer` en sí** (`CREATE TABLE IF NOT EXISTS` / `CREATE UNIQUE INDEX IF NOT EXISTS`) porque ya existe en producción (vacía, huérfana de una migración que nunca llegó a este repo) pero no en test/desarrollo — ver la sección "Contexto" del spec antes de tocar `prisma/schema.prisma`.
- **No se edita el nombre de un cliente existente desde el flujo de venta** — si el teléfono matchea, se usa ese cliente tal cual, cualquier nombre tipeado se ignora.
- **Idioma:** UI, rutas y mensajes de error en español; identificadores de código en inglés.
- **Commits:** uno por tarea como mínimo, Conventional Commits, terminando con `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>` — literal, siempre, sin importar qué modelo hizo el trabajo (ver nota más abajo).

**Nota sobre atribución de commits:** en la implementación del módulo de Ventas, dos implementadores en modelos económicos se auto-atribuyeron en el trailer del commit ("Claude Haiku 4.5") en vez de usar la convención fija del proyecto, a pesar de que el dispatch se lo pedía explícitamente. Cada dispatcher de este plan debe instruir el trailer exacto y **verificar con `git log -1` después de cada commit** — si no coincide textualmente, corregirlo antes de reportar la tarea como terminada.

## Review Focus

- **El mismo teléfono tipeado con formato distinto en dos ventas separadas** (con espacios, guiones, con/sin `15`, etc.) debe terminar siendo el mismo cliente — nunca crear un `Customer` duplicado por una diferencia de formato. Cubierto en Task 2 (normalización) y Task 3 (`createSale`).
- **Teléfono nuevo cargado dos veces "a la vez"** (dos ventas concurrentes con el mismo teléfono que todavía no existe como cliente): la segunda no debe romper la venta ni el request completo — debe resolverse sola, enlazando al cliente que la primera acaba de crear. Cubierto en Task 3.
- **Teléfono con contenido pero sin nombre, para un cliente que no existe todavía**: la venta debe rechazarse con un mensaje claro, sin persistir nada (ni el cliente, ni la venta, ni el descuento de stock). Cubierto en Task 3.
- **`listCustomers` no debe contar ventas anuladas** como compras ni sumarlas al gasto total — un cliente con una única venta luego anulada no debe figurar como comprador ni como recurrente. Cubierto en Task 2.
- **`resetDb()` (helper de tests) no limpiaba la tabla `Customer`** hasta esta iteración — a diferencia de `Sale`/`SaleItem` (que se limpian transitivamente por `CASCADE` al truncar `User`), `Customer` no es referenciada por ninguna tabla que sí se trunque, así que sin agregarla explícitamente, los datos de cliente de un test quedarían visibles en el siguiente y romperían la unicidad de `phone` entre tests. Cubierto en Task 1.

```ts
import 'server-only'
import { prisma } from '@/server/db'
import { toNumber } from '@/lib/pricing'
import { normalizePhone } from '@/lib/phone'

export async function getCustomerByPhone(rawPhone: string): Promise<{ id: string; name: string; phone: string } | null> {
  const phone = normalizePhone(rawPhone)
  if (phone.length < 6) return null
  return prisma.customer.findUnique({ where: { phone }, select: { id: true, name: true, phone: true } })
}

export type CustomerRow = {
  id: string; name: string; phone: string
  purchaseCount: number; totalSpent: number; isRecurring: boolean
}

export async function listCustomers(): Promise<CustomerRow[]> {
  const rows = await prisma.customer.findMany({
    include: { sales: { where: { cancelledAt: null }, select: { total: true } } },
    orderBy: { name: 'asc' },
  })
  return rows.map((c) => {
    const purchaseCount = c.sales.length
    const totalSpent = c.sales.reduce((sum, s) => sum + (toNumber(s.total) ?? 0), 0)
    return { id: c.id, name: c.name, phone: c.phone, purchaseCount, totalSpent, isRecurring: purchaseCount >= 2 }
  })
}
```
